Start in 10 Minutes

This is the minimum safe path for a team that wants to trial the kit without reading the entire document first.

1. Copy the kit Vendor or copy skills/, adapters, and scripts into the target repository.
2. Scaffold folders Run scripts/bootstrap-aiddk.sh to create memory and artifact folders.
3. Pick an adapter Place the appropriate entrypoint at the repo root, such as AGENTS.md.
4. Create durable context Run /aiddk-memory and refine the starter memory files.
5. Start the first feature Run /aiddk-spec with a real feature slug and lock the acceptance criteria.
Success looks like: a real feature has spec.md, a traceable task breakdown, bounded implementation, and fresh verification evidence before merge.

Proposal Summary

Use this kit when you want AI coding to behave like a disciplined engineering workflow instead of a chat session with weak memory and weak verification.
Problem Ad hoc AI coding drifts because intent, decisions, and proof are scattered across chat history.
Mechanism The kit anchors work to skills, durable artifacts, and explicit verification rules.
Outcome Teams get cleaner reviews, resumable sessions, and less ambiguity between request and code.

2. Purpose and Value

What Problem This Kit Solves

  • Agent Drift: AI implementation diverges from real user intent.
  • Context Loss: long sessions lose rationale and decisions.
  • Weak Verifiability: changes look plausible but are not evidence-backed.

What Users Get

  • Clear intent: requirements are locked before implementation.
  • Traceability: requirement -> task -> validation remains explicit.
  • Durability: artifacts survive chat/session resets.
  • Operational discipline: completion requires fresh evidence, not assumptions.

3. System Architecture

A. The Skill Layer (Logic)

Located in skills/. Defines the Engineering Contract—what to read, how to operate, and when to stop.

B. The Adapter Layer (Entry)

Root entrypoints (AGENTS.md, etc.). Enforces the "Skill-First" rule to prevent agent improvisation.

C. The Artifact Layer (State)

Located in artifacts/features/. The durable source of truth that survives session resets.

Memory Tiers:

  • Project Memory: Shared team conventions (memories/repo/).
  • Private Memory: Local machine-specific notes (not committed).
  • Global Memory: Personal cross-project preferences.

Core Design Principles

  • Artifact-First: if it is not in an artifact, it is not durable enough to guide implementation.
  • Surgicality: every change should trace back to a task or requirement.
  • Continuity-First: end long sessions with a handoff, not a vague chat summary.
  • Evidence-Based Verification: "done" means fresh proof, not a plausible diff.
  • Client-Decoupled Execution: skills define the contract; adapters stay thin.

Minimum Safe Repository Shape

skills/
memories/repo/
artifacts/features/
AGENTS.md

Bootstrap scaffolds folders and starter memory files. It does not install skills/; users must copy or vendor them into the target repository.

Canonical Memory Files

File or Folder Role What Belongs There
memories/repo/constitution.md Normative rules Guardrails, non-negotiable quality rules, and durable operating constraints.
memories/repo/project-knowledge-base.md Descriptive memory Architecture notes, subsystem boundaries, recurring patterns, and brownfield watchouts.
artifacts/features/<slug>/ Change-specific state Analysis, spec, plan, tasks, review, and handoff for one bounded feature or fix.

Memory Promotion Rules

  • Promote a finding into repo memory only when it is durable, evidence-backed, and useful beyond one feature.
  • Keep feature-local notes, temporary debugging context, and one-off rationale inside feature artifacts.
  • Do not create competing durable memory files such as AI_CONTRACT.md, ARCHITECTURE.md, or DECISIONS.md unless the repository intentionally changes the canonical model.

Agentic Data Flow

User Request → Adapter → Skill Contract → Artifacts → Implementation → Verification

The kit sits between the request and the code change. The adapter routes work into a skill, the skill reads and writes artifacts, and the implementation is judged against those artifacts instead of chat history.

Common Feedback Loops

  • Discovery loop: implementation uncovers unknown behavior, so work moves back to research or planning.
  • Clarification loop: planning reveals requirement gaps, so work returns to the spec.
  • Drift loop: verification finds behavior outside the approved artifacts, so code or spec must be corrected.

The Quality Bar

  • Downstream stages do not invent requirements.
  • Implementation is backed by fresh evidence.
  • Traceability from request to proof remains intact.
  • Spec and code stay aligned at the time of merge.

6. How to Use (Playbooks)

Quick Start Contract

  • Repository must contain skills/, memories/repo/, and artifacts/features/.
  • Bootstrap only scaffolds folders and starter memory files; it does not install skills.
  • Implementation is invalid without task traceability and fresh evidence.
  • Before ending a long session, always emit a handoff artifact.
Artifact First Evidence Based Subagent Driven Continuity First Surgical Changes

First Commands

If durable repo memory does not exist yet, start here:

/aiddk-memory

Then create a new feature with a slug:

/aiddk-spec
Feature slug: my-first-feature

Playbook by Goal

Goal Start Command Expected Artifact Next Command
New feature with uncertainty /aiddk-research analysis.md /aiddk-spec
Feature with clear requirements /aiddk-spec spec.md /aiddk-plan
Implementation work /aiddk-implement Code plus tests /aiddk-verify
Session continuity /aiddk-handoff handoff.md Resume with next-step prompt

Playbook by Role

  • New user: run bootstrap, then /aiddk-memory, then /aiddk-spec.
  • Feature engineer: follow Spec -> Plan -> Implement -> Verify in order.
  • Architect: use /aiddk-diagram and /aiddk-adr before coding.
  • Maintainer: enforce consistency checks and release dry-runs.

When Blocked, Move Upstream

  • Unclear behavior: return to /aiddk-research.
  • Weak requirements: refine with /aiddk-spec.
  • Design ambiguity: extend /aiddk-plan with design.md.
  • Weak evidence: rerun implementation validation or use /aiddk-verify.

Ready for Implement

  • Spec readiness: the user scenarios and acceptance criteria are specific enough that implementation does not need to invent behavior.
  • Task readiness: tasks.md breaks the work into reviewable slices with clear ownership.
  • Design readiness: ambiguous architectural choices are resolved in design.md or ADRs.
  • Validation readiness: each task has an intended proof path before code starts.

Definition of Done

  • Task state, code changes, and fresh validation evidence all agree.
  • The implemented behavior maps back to the approved spec and task IDs.
  • Drift discovered during verification is either removed or promoted upstream into artifacts.
  • A handoff is written if the work stops before the next bounded step is obvious.

When Artifacts Disagree

If This Disagrees With This Correct Move
Implementation spec.md Do not rationalize it in chat. Either remove the behavior or update the spec first.
tasks.md spec.md Return to planning and restore requirement coverage before resuming implementation.
review.md Observed code or tests Fix the evidence gap. The review is wrong if it cannot prove the behavior.
Repo memory Observed codebase reality Promote corrected knowledge with /aiddk-memory; do not let stale memory govern new work.

Workflow Examples: Greenfield and Brownfield

Project Type When to Use Recommended Flow Main Outputs
Greenfield New product, new service, or major rewrite with no stable baseline. Memory -> Research -> Spec -> Diagram -> ADR -> Plan -> Implement -> Verify -> Handoff Project constitution, architecture decisions, feature plan, verified implementation
Brownfield Existing system where safety, compatibility, and migration risks are critical. Memory -> Research -> Spec -> Plan -> Implement -> Verify -> Cleanup -> Handoff Impact analysis, scoped spec, incremental tasks, regression evidence

Greenfield Example (new platform module)

1. Capture principles and constraints with /aiddk-memory.

2. Run /aiddk-research to explore domain unknowns and constraints.

3. Produce acceptance criteria using /aiddk-spec.

4. Draft architecture and boundaries with /aiddk-diagram and /aiddk-adr.

5. Convert scope into atomic tasks with /aiddk-plan.

6. Implement incrementally via /aiddk-implement and confirm with /aiddk-verify.

7. Publish continuity with /aiddk-handoff.

Memory → Research → Spec → Diagram → ADR → Plan → Implement → Verify → Handoff

Brownfield Example (feature change in production system)

1. Start from existing repo context in /aiddk-memory to avoid relearning architecture.

2. Use /aiddk-research to locate integration points, constraints, and regressions.

3. Define compatibility and rollback criteria in /aiddk-spec.

4. Break work into low-risk slices using /aiddk-plan.

5. Execute one slice at a time with /aiddk-implement and validate each slice with /aiddk-verify.

6. Run /aiddk-cleanup to remove temporary scaffolding and detect drift.

7. End with /aiddk-handoff so the next session can resume safely.

Memory → Research → Spec → Plan → Implement Slice → Verify Slice → More Slices?

No → Cleanup → Handoff

Delivery Tutorial Snapshot

Reference feature flow:

1. Research: use /aiddk-research when root cause is unknown.

2. Spec: use /aiddk-spec with clarifying questions.

3. Plan: use /aiddk-plan for atomic traceable tasks.

4. Implement: run /aiddk-implement task-by-task.

5. Verify: run /aiddk-verify for drift and evidence audit.

Session Handoff Pattern

  1. Run /aiddk-handoff before ending a long session.
  2. Write blockers, progress, and the next immediate task into handoff.md.
  3. Resume by pasting the generated next-step prompt into a fresh session.

Brownfield Adoption Rules

  • Do not backfill: write artifacts for the new change, not the entire legacy codebase.
  • Analysis first: in brownfield repositories, prefer /aiddk-research before scoping the change.
  • Gradual memory: promote one durable pattern at a time instead of writing a giant knowledge base up front.

Multi-Agent Coordination

  • Phase locking: only one agent edits a locked planning artifact such as spec.md or plan.md at a time.
  • Task ownership: assign explicit task IDs when multiple agents implement in parallel.
  • Branch isolation: reintegrate only after verification passes.
  • Shared memory: durable discoveries should be promoted so later agents do not repeat the same exploration.

What Not To Do

  • Do not treat chat as more authoritative than artifacts.
  • Do not skip quality gates because the change feels small.
  • Do not broaden scope silently during implementation.
  • Do not mark work complete without fresh validation evidence.

Proof of Workflow

What Good Looks Like

A useful proposal document needs one concrete walkthrough. This example shows how a request becomes a verified change without relying on chat memory.

Request → Research → Spec → Plan → Implement → Verify → Handoff or Merge

1. Request

Example: "Add social login without breaking existing email login."

The request is still intent, not implementation. The kit does not let coding start here.

2. Spec

Output: spec.md records scenarios, acceptance criteria, and compatibility constraints.

This is where "must not break existing email login" becomes a testable rule instead of a vague preference.

3. Plan

Output: plan.md and tasks.md split the work into schema updates, provider integration, UI changes, and verification tasks.

The implementation no longer decides scope on the fly.

4. Implement

Output: code plus bounded tests mapped back to task IDs.

Each slice is small enough to review without reconstructing the whole feature from chat history.

5. Verify

Output: review.md records whether the feature satisfies the spec and whether the evidence is fresh.

This is where drift is caught before merge instead of after release.

6. Continuity

Output: handoff.md if the work pauses, or clean merge evidence if it finishes.

The next person or next agent can resume without re-discovering intent.

Standard Templates

Canonical structures for kit artifacts.

spec-template.md

  • Metadata: Name, Slug, Owner, Status.
  • Problem Statement: Why this change matters.
  • Outcomes & Success Criteria: What "done" looks like.
  • User Stories & Scenarios: Happy path, Edge case, Error state.
  • Functional Requirements: REQ-001, REQ-002...
  • Acceptance Criteria: AC-001, AC-002 (linked to REQs).

tasks-template.md

  • Task Formatting: - [ ] TASK-001 Status: Not Started.
  • Phases: Foundations, Core Implementation, Validation.
  • Traceability: Link to REQs and ACs.
  • TDD Requirement: Identify RED (failing test) and GREEN (passing) for behavioral changes.

adr-template.md

  • Context: The forces and problems at play.
  • Decision: What is being proposed and why.
  • Options: Dimensional assessment (Complexity, Cost, Scalability).
  • Consequences: What becomes easier or harder.

analysis-template.md

  • Diagnose Loop: Reproduce -> Hypothesize -> Instrument -> Conclusion.
  • Findings: Fact vs Inference.
  • Risks & Unknowns: Proving steps for uncertainties.

handoff-template.md

  • Current Progress: Tasks completed and in progress.
  • Active Blockers: Technical issues or ambiguities.
  • Next Immediate Step: Task ID, Goal, and Files to focus on.
  • Resume Prompt: Standardized copy-paste instruction for the next session.

requirements-review.md

  • Verdict: ready | ready with minor issues | not ready.
  • Readiness Assessment: Strengths and main concerns.
  • Traceability Check: Requirements covered, ACs testable.
  • Blocking Issues: BR-001, recommended resolution.

10. FAQ and Common Mistakes

FAQ

Do I need all 10 skills for every change?
Not always. Use a delivery profile. Small changes can run Fast-Track; risky changes should use the full path.

Can I skip spec and go straight to code?
Only for truly trivial changes. For behavioral changes, skip-spec creates drift risk and weak verification.

What does "done" mean?
Done means task state, code change, and fresh validation evidence all agree.

When should I use handoff?
Before ending any long session, model switch, or context-heavy branch of work.

Common Mistakes

  • Treating chat as source-of-truth instead of artifacts.
  • Marking tasks done before running validation.
  • Mixing unrelated refactors into implementation tasks.
  • Skipping memory promotion for durable findings.
  • Deleting markdown docs before HTML parity is truly stable.

Adoption Pitfalls

  • "The overhead is too high for small fixes." Use Fast-Track only for truly low-risk work.
  • "Agents are ignoring the skills." Tighten the adapter and make the Skill-First rule explicit.
  • "Artifacts are drifting from the code." Make verification a mandatory review gate.
